The Idea
핵심 아이디어

A knowledge management system should document itself — both for the human who maintains it and for the AI that reads it. 지식관리 시스템은 스스로를 문서화해야 한다 — 유지하는 사람에게도, 읽어주는 AI에게도.

CMDS (커맨드스페이스) is a Personal Knowledge Management system that has grown past 14,000 notes across 87 subcategories. At that scale, the system itself needs rules — where files go, how they're named, what properties they carry, which conventions agents must follow.

These system files are those rules. They're loaded into every Claude Code session as context. They're read by Gemini, Codex, and Cursor. And now they're shared so you can fork the architecture for your own vault.

CMDS(커맨드스페이스)는 87개 하위 카테고리와 14,000개 노트 규모로 성장한 개인 지식관리 시스템입니다. 그 규모에서는 시스템 자체에 규칙이 필요합니다 — 파일이 어디 가는지, 이름은 어떻게 짓는지, 어떤 프로퍼티를 갖는지, 에이전트는 어떤 관행을 따라야 하는지.

이 시스템 파일들이 바로 그 규칙입니다. Claude Code 세션마다 컨텍스트로 로드되고, Gemini·Codex·Cursor가 읽으며, 이제 여러분의 볼트를 위해 포크할 수 있도록 공개됩니다.

The Architecture 아키텍처

Six files, ordered by precedence. 여섯 개 파일, 우선순위 순으로 로드.

Each file serves a distinct audience. @include directives pull shared rules inline; precedence numbers settle conflicts when two files give different advice. 각 파일은 분명한 대상 독자를 가집니다. @include 디렉티브로 공유 규칙을 인라인 로드하고, 두 파일이 충돌할 때는 precedence 숫자가 판정합니다.

Nine files make up the system, but no agent reads all nine. Claude Code opens one file, CLAUDE.md, which pulls in the nine shared rules and CMDS.md on every session; Claude Code reads DESIGN.md, AGENTS.md and ANTIGRAVITY.md only when a task calls for them. The two BRAIN files belong to the Gobi app and never enter a coding agent's context, and CMDS Guide and CMDS Head Quarter are reference documents you open when you need standards or navigation. 시스템 파일은 아홉 개지만 에이전트가 아홉 개를 다 읽지는 않습니다. Claude Code는 CLAUDE.md 하나를 열고, CLAUDE.md가 매 세션 공유 규칙 9개와 CMDS.md를 불러오며, DESIGN.md·AGENTS.md·ANTIGRAVITY.md는 해당 작업이 생길 때만 읽습니다. BRAIN 두 파일은 Gobi 앱 전용이라 코딩 에이전트의 컨텍스트에 들어오지 않고, CMDS Guide와 CMDS Head Quarter는 표준이나 길찾기가 필요할 때 펴 보는 참고 문서입니다.

The CMDS Process CMDS 프로세스

Four verbs. Four stages. One lifecycle. 네 개의 동사, 네 개의 단계, 하나의 생애주기.

Every note travels the same path — captured, integrated, developed, shared. Each stage has a matching slash command that encodes the workflow. 모든 노트는 같은 길을 지나갑니다 — 포착, 통합, 발전, 공유. 각 단계는 해당 워크플로를 인코딩한 슬래시 커맨드를 갖습니다.

Every note in the vault moves through the same four stages. Connect captures and links it (/connect, 100 Themes), Merge turns several sources into one synthesized note (/merge, 200 Literature), Develop applies methods and tools (/develop, 300–600), and Share produces outputs (/share, 700–800). Cross-cutting commands such as /inbox, /lint, /query and /status work at any stage. 볼트의 모든 노트는 같은 네 단계를 지납니다. Connect는 노트를 수집하고 연결하며(/connect, 100 Themes), Merge는 여러 출처를 하나의 통합 노트로 만들고(/merge, 200 Literature), Develop은 방법과 도구를 적용하며(/develop, 300–600), Share는 산출물을 만듭니다(/share, 700–800). /inbox, /lint, /query, /status 같은 가로 커맨드는 어느 단계에서나 쓸 수 있습니다.

These files are edited only in the vault. One script, sync-system-files.sh, fans the source out to eight destinations: a backup and a sanitized share copy inside the vault, the DEV folder with its ZIP, and from that folder a GitHub push with tag and Release and the Vercel deploy that serves this site (GitHub does not deploy on its own). It then checks three satellites, the cmds-vault starter kit, CMDS_LLM_Wiki, and the LLM Wiki starter kit, and reports any drift from the source. 이 파일들은 볼트에서만 고칩니다. 스크립트 sync-system-files.sh 하나가 원본을 여덟 곳으로 퍼뜨립니다. 볼트 안의 백업과 sanitized 공유본, DEV 폴더와 ZIP, 그리고 그 폴더에서 나가는 태그·Release 붙인 GitHub push와 이 사이트를 띄우는 Vercel 배포입니다(GitHub가 스스로 배포하지는 않습니다). 마지막으로 cmds-vault 스타터킷, CMDS_LLM_Wiki, LLM Wiki 스타터킷 세 위성을 점검해 원본과 벌어진 곳을 보고합니다.

The 9 Categories 9개 카테고리

Every note has a home. 모든 노트는 갈 곳이 있습니다.

100 through 900 — a numeric hierarchy inspired by academic taxonomies. 87 subcategories. 14,000+ notes know where they belong. 100부터 900까지 — 학문적 분류 체계에서 영감을 받은 숫자 계층. 87개의 하위 카테고리. 만 사천 개가 넘는 노트가 자신의 자리를 압니다.

Every note in the vault is assigned to one of nine categories, 100 Themes through 900 Divisions, which together hold 87 subcategories. The assignment is metadata, not a folder: a note carries a CMDS: value pointing at one subcategory, so it can sit anywhere in the folder tree and still have a numbered home. The map below shows the nine categories with example subcategories. 볼트의 모든 노트는 100 Themes부터 900 Divisions까지 아홉 카테고리 중 하나에 속하고, 그 아래에 서브카테고리 87개가 있습니다. 이 분류는 폴더가 아니라 메타데이터입니다. 노트는 frontmatter의 CMDS: 값으로 서브카테고리 하나를 가리키므로, 폴더 트리 어디에 있든 숫자로 된 집을 갖습니다. 아래 지도는 아홉 카테고리와 예시 서브카테고리를 보여 줍니다.

Inside a note 노트 한 편의 내부

Seven required properties.
Every note. No exception. 일곱 가지 필수 프로퍼티.
모든 노트. 예외 없음.

Structured frontmatter is how AI agents tell notes apart at scale. English description fields double as relevance hints for LLM search. 구조화된 frontmatter는 AI 에이전트가 대량의 노트를 구분하는 방식입니다. 영어로 쓴 description 필드는 LLM 검색의 관련성 힌트 역할을 겸합니다.

--- type: note aliases: [] description: "Meeting minutes from 2026-04-07 retrospective. Contains feedback summary and next-action items." author: - "[[Yohan Koo]]" date created: 2026-04-18 date modified: 2026-04-18 tags: [CMDS, meeting] # optional CMDS: "[[📚 831 Consulting]]" status: completed ---

A note's folder and its classification are two different axes. The folder (one of the ten root folders, 00 to 90) only says where the file lives; what the note is comes from its frontmatter. Every note carries seven required fields (type, aliases, description, author, date created, date modified, tags), and the optional CMDS: field points to one of the 87 subcategories in the 100–900 system, with index: linking an index note and status: holding one of five values. 노트의 폴더와 분류는 서로 다른 축입니다. 폴더(루트 폴더 10개, 00~90 중 하나)는 파일이 어디 있는지만 말하고, 노트가 무엇인지는 frontmatter가 말합니다. 모든 노트에는 필수 7필드(type, aliases, description, author, date created, date modified, tags)가 있고, 선택 필드 CMDS:는 100~900 체계의 87개 서브카테고리 중 하나를 가리키며, index:는 인덱스 노트를, status:는 다섯 값 중 하나를 담습니다.
